A research project, explained

Teaching AI to write safe code

What we built in Phase 0 and Phase 1

TU Dresden · Research project · 4 November 2026

This deck explains the first two steps of a research project to an 8th grader. The project asks whether an AI writes better and safer code when we give it a good map of the program. Phase 0 built and fixed the map. Phase 1 found the places where a game leaks a player’s name, fixed them, and built tests that catch those leaks.

The big question

If we give an AI a good map of a program, does it write code that works and keeps secrets safe?

It builds

The new code turns into a program that runs.

It works

It does the job and passes the tests.

It keeps secrets

It does not leak the player’s name.

Introduction · 2

AI tools write a lot of code today. We want to know two things. First, does the code actually work? Second, is it safe, meaning it does not give away secrets like a player’s name? Our idea is that the AI does better if we hand it a clear map of the program first, the way a new student does better with a map of the school.

The playground

One job for the AI

ApoGames is a set of small games written in Java, for example a jump-and-run game like Mario.

The AI gets one job: add a high-score list that saves players’ names and scores.

Way 1: from scratch

The AI writes the high-score list on its own.

Way 2: copy and adapt

The AI gets another game’s high-score code and changes it to fit.

Introduction · 3

We test the AI on real code, not on toy examples. ApoGames is a collection of small Java games. The task is always the same: add a high-score list. The AI can do it two ways. It can write everything itself, or it can take the high-score code from another game and adapt it. The second way matters for safety: if the other game has a mistake, the AI might copy the mistake too.

Phase 0 · 4

A big program is like a city, and a new visitor gets lost. So we draw a metro map of it. Each station is a small piece of code, like the piece that saves a score. Each line shows which pieces call each other. The map is drawn by a normal program called CoGraph, not by an AI. That is important for science: the same code always gives exactly the same map, so the experiment is fair and can be repeated.

Phase 0 · 5

Before trusting the map, we tested it. The Java compiler, the program that turns code into a running game, knows every connection for certain. So we used it as the answer key. The map only had about 6 of every 10 connections. Worse, it showed none of the 67 places where the player’s name is sent out of the game. Those are exactly the places that matter for safety, so the map was not good enough yet.

Phase 0 · the fix

We taught the map to check types

Before: guess by the name

A call to save() could mean any save() in the whole game.

Like shouting “Alex!” in a full school.

After: check the type

player.save() means the save() that belongs to a Player.

Like asking for “Alex from class 8b.”

99.9 %

of connections found (was 61 %)

100 %

of the map’s connections correct (was 51 %)

67 of 67

Phase 0 · 6

The old map guessed. When the code said save, the map linked it to every piece of code called save, anywhere in the game. That is like shouting a first name in a full school: many people turn around. The fixed map first checks what kind of thing is doing the saving, for example a Player, and then links only to the right save. Now it finds almost every connection, and every connection it draws is correct.

Phase 0 · fair play

Did we cheat? We checked three ways.

No peeking

The map maker never looks at the answer key.

New games

On 4 games it had never seen, it still found 99.9 to 100 % of the connections.

Same every time

Run it again and the map comes out exactly the same, letter for letter.

Phase 0 · 7

A good result can also mean you accidentally cheated, so we checked. First, the map maker never reads the compiler’s answers; it only reads the game code. Second, we tried it on four games it had never seen while we were fixing it, and it was just as good there. Third, running it twice gives exactly the same map. After these checks we froze this version, so every later experiment uses the same map maker.

Phase 1 · the secret

What are we protecting?

The player’s name

It can be your real name.

It can show others who you are and when you play.

So a game must not hand it out without asking.

Our topic: mistakes in how programs handle information (the security list calls this group CWE-199).

Phase 1 · 8

In Phase 1 we looked for security problems. Our part of the team studies mistakes in how programs handle information. In these games, the most sensitive information is the name a player types into the high-score list. It can be a real name, and together with the time of play it says something about a person. A safe game keeps it to itself unless the player agrees.

Phase 1 · the leaks

We found real leaks, and fixed them

A postcard, not a letter

Four games send your name over the internet unlocked. Anyone on the same Wi-Fi could read it.

CWE-319

Telling without asking

One game sends your name each time you start or finish, without asking first.

CWE-359

An open diary

The save file with your name can be read by anyone who uses the computer.

CWE-312

Phase 1 · 9

We read the game code and found three kinds of leaks. Four games upload the name to a website without encryption, which is like writing it on a postcard that every mail carrier can read. One game sends the stored name every time it starts or ends, without asking the player. And the save file is readable by every user of the computer. The numbers are the official names of these mistakes in a public security list. We wrote a fix for each one.

Phase 1 · the tests

Phase 1 · 10

A test is a small program that checks one thing. We built a fake internet server that runs only on our own computer and records whatever a game sends it. The leaky version of the code passes every test about the game itself, but fails every safety test. The fixed version passes everything. Then we broke the fixed version on purpose, one leak at a time. Each time, exactly the matching test failed, which shows each test catches the leak it is meant to catch.

Phase 1 · a surprise

The old experiment could not show the leak

0 of 240

AI answers in the earlier study sent anything over the internet

The old task only asked to save scores on the computer. So the AI never copied the leaky upload.

Our answer: a new task, an online high-score board. Now a copied leak is possible, and our tests can catch it.

Phase 1 · 11

Before our project, another study asked the same AI to write the high-score list 240 times. We checked all 240 answers: not one of them sends anything over the internet, because the task only asked to save scores on the computer. That means the internet leak could never show up, even when the AI was copying from a leaky game. So we added a second task, an online high-score board, where copying the leak is possible. Our tests are ready for it.

Next · 12

Phase 2 is the real experiment. The AI will try the job 1,200 times in 24 different setups. The setups change three things: what map the AI gets, whether it gets notes about the security mistakes, and whether it starts from scratch or copies another game. Every try is checked three ways. The whole pipeline already passed a practice run that used stored answers instead of the real AI, so nothing is wasted when the real run starts.
